# 클로드 스킬(Claude Agent Skills) 정리

> 조사일: 2026-09-21 · 출처: Anthropic 공식 문서(platform.claude.com, code.claude.com), anthropics/skills 저장소

---

## 1. 스킬이란?

**스킬(Agent Skill)** 은 클로드에게 "특정 작업을 이렇게 처리해라"라고 가르치는 **폴더 하나**다.
지시문(markdown), 참고 자료, 실행 스크립트를 묶어놓으면, 클로드가 **필요할 때만 알아서 꺼내 쓴다.**

- 프롬프트: 대화 한 번에만 유효 → 매번 다시 붙여넣어야 함
- CLAUDE.md: 항상 전체가 컨텍스트에 올라감 → 길어지면 낭비
- **스킬: 평소엔 이름+설명만 올라가고, 관련 작업일 때만 본문이 로드됨**

한 문장으로: *범용 에이전트를 특정 분야 전문가로 바꾸는, 재사용 가능한 온보딩 문서.*

### 왜 쓰는가

| 이점 | 설명 |
|---|---|
| 전문화 | 우리 회사 브랜드 가이드, 사내 DB 스키마, 팀 워크플로를 클로드에 주입 |
| 반복 제거 | 한 번 만들면 이후 대화마다 자동 적용 |
| 조합 가능 | 여러 스킬이 한 작업에서 함께 동작 |
| 컨텍스트 절약 | 설치해도 안 쓰면 토큰 비용 ≈ 0 |

## 2. 핵심 구조 — SKILL.md

모든 스킬은 폴더 + `SKILL.md` 하나로 시작한다.

```
my-skill/
├── SKILL.md          # 필수: 메타데이터 + 지시문
├── reference.md      # 선택: 상세 참고 문서
├── examples.md       # 선택: 예시 모음
└── scripts/
    └── helper.py     # 선택: 실행 스크립트
```

`SKILL.md` 최소 형태:

```markdown
---
name: pdf-processing
description: PDF에서 텍스트·표를 추출하고, 양식을 채우고, 문서를 병합한다. PDF 파일을 다루거나 사용자가 PDF, 양식, 문서 추출을 언급할 때 사용한다.
---

# PDF Processing

## Quick start
pdfplumber로 텍스트를 추출한다:
...

## 고급 기능
양식 채우기는 [FORMS.md](FORMS.md) 참고.
```

### 필수 필드 규칙

| 필드 | 제약 |
|---|---|
| `name` | 최대 64자, **소문자·숫자·하이픈만**, XML 태그 불가, 예약어(`anthropic`, `claude`) 불가 |
| `description` | 비어 있으면 안 됨, 최대 1024자, XML 태그 불가, **"무엇을 하는지 + 언제 쓰는지" 둘 다** 포함 |

> ⚠️ `description`은 클로드가 "이 스킬을 지금 쓸까?"를 판단하는 **유일한 근거**다. 여기가 부실하면 스킬이 아예 발동하지 않는다.

## 3. 동작 원리 — 점진적 공개(Progressive Disclosure)

스킬은 파일 시스템 기반이라, 클로드가 **단계별로 필요한 만큼만** 읽어 들인다.

| 단계 | 로드 시점 | 토큰 비용 | 내용 |
|---|---|---|---|
| **Level 1: 메타데이터** | 항상 (세션 시작 시) | 스킬당 약 100토큰 | frontmatter의 `name`, `description` |
| **Level 2: 지시문** | 스킬이 발동됐을 때 | 5k 토큰 이하 권장 | SKILL.md 본문 |
| **Level 3: 리소스** | 실제로 참조할 때 | 읽기 전엔 0 | 추가 md 파일, 스크립트, 데이터 |

동작 흐름 예시:

1. **시작** — 시스템 프롬프트에 `pdf-processing - PDF에서 텍스트·표를 추출하고...` 한 줄만 들어감
2. **요청** — "이 PDF에서 텍스트 뽑아서 요약해줘"
3. **로드** — 클로드가 bash로 `cat pdf-processing/SKILL.md` 실행 → 지시문이 컨텍스트에 들어옴
4. **판단** — 양식 채우기는 필요 없으니 `FORMS.md`는 **읽지 않음**
5. **실행** — 지시문대로 작업 수행

### 이 구조가 주는 이점

- **온디맨드 파일 접근**: 참고 파일 수십 개를 번들해도, 안 읽으면 토큰 0
- **스크립트 효율**: `validate.py`를 실행하면 **코드가 아니라 출력만** 컨텍스트에 들어감
- **번들 용량 제한 사실상 없음**: 방대한 API 문서, 대용량 데이터셋도 부담 없이 포함 가능

## 4. 어디서 쓸 수 있나

| 환경 | 지원 | 설치 방식 | 공유 범위 |
|---|---|---|---|
| **Claude Code** | 커스텀 스킬 | 파일 시스템 (`~/.claude/skills/`, `.claude/skills/`) | 개인 / 프로젝트 / 플러그인 |
| **claude.ai** | 사전 제작 + 커스텀 | 설정 > Features 에서 zip 업로드 | **사용자 개인** (조직 공유·중앙관리 불가) |
| **Claude API** | 사전 제작 + 커스텀 | `/v1/skills` 업로드 후 `container`에 `skill_id` 지정 | 워크스페이스 전체 |
| **AWS / MS Foundry** | API와 동일 | Skills API | 워크스페이스 |

> ⚠️ **스킬은 환경 간 자동 동기화되지 않는다.** claude.ai에 올린 스킬은 API에서 못 쓰고, 반대도 마찬가지다. 쓰려는 곳마다 따로 올려야 한다.

API에서 스킬을 쓰려면 **코드 실행(code execution) 도구**가 필요하다. 스킬은 그 컨테이너 안에서 돈다.

### 런타임 제약

- **Claude Code**: 네트워크 풀 액세스(내 컴퓨터와 동일). 단, 전역 패키지 설치는 지양
- **Claude API**: **네트워크 차단**, 런타임 패키지 설치 불가, 사전 설치 패키지만 사용 가능
- **claude.ai**: 설정에 따라 네트워크 전체/일부/차단

### 기본 제공 스킬

- 사전 제작: **pptx**(파워포인트), **xlsx**(엑셀), **docx**(워드), **pdf** — API·claude.ai에서 즉시 사용
  (참고: Claude Code에서는 이 문서 스킬들이 기본 제공되지 않는다)
- 오픈소스: [anthropics/skills](https://github.com/anthropics/skills) 저장소
  (`claude-api`, `skill-creator`, `mcp-builder`, `frontend-design`, `canvas-design`, `brand-guidelines`, `webapp-testing`, `algorithmic-art`, `theme-factory`, `doc-coauthoring`, `internal-comms` 등)
  - 설치: Claude Code에서 `/plugin marketplace add anthropics/skills` → `document-skills` 또는 `example-skills` 플러그인 설치
  - 데모·교육 목적으로 제공되며 실서비스 전 검증 권장. 대부분 Apache 2.0, 문서 스킬은 source-available

## 5. Claude Code에서의 스킬 (실전)

### 스킬이 놓이는 위치

| 종류 | 경로 | 적용 범위 |
|---|---|---|
| 개인 | `~/.claude/skills/<name>/SKILL.md` | 내 모든 프로젝트 |
| 프로젝트 | `.claude/skills/<name>/SKILL.md` | 해당 저장소, 팀과 공유 |
| 하위 디렉터리 | `<subdir>/.claude/skills/...` | 그 디렉터리 이하 세션 |
| 엔터프라이즈 | 관리 설정 디렉터리의 `.claude/skills/` | 조직 전체 |
| 플러그인 | `<plugin>/skills/<name>/SKILL.md` | `/plugin-name:skill-name` 으로 호출 |

이름 충돌 시 우선순위: **엔터프라이즈 > 개인 > 프로젝트**, 로컬 스킬이 번들 스킬을 덮어씀.

### 확장 frontmatter (Claude Code 전용)

| 필드 | 용도 |
|---|---|
| `disable-model-invocation: true` | 클로드 자동 발동 금지, 사용자가 `/명령`으로만 실행 (배포·커밋 등) |
| `user-invocable: false` | 사용자는 못 부르고 클로드만 참고 (배경 지식용) |
| `allowed-tools` / `disallowed-tools` | 도구 사전 승인 / 차단 (승인은 다음 메시지에 만료) |
| `model`, `effort` | 이 스킬 실행 시 모델·사고 수준 지정 |
| `context: fork`, `agent`, `background` | 서브에이전트에서 격리 실행 |
| `arguments`, `argument-hint` | `/fix-issue 123` 처럼 인자 받기 (`$ARGUMENTS`, `$name`, `$0`) |
| `paths` | 특정 파일 패턴일 때만 자동 발동 |
| `hooks`, `metadata`, `license` | 훅 등록, 자유 메타데이터, 라이선스 |

### 동적 컨텍스트 주입

클로드가 읽기 **전에** 셸 명령을 실행해 결과를 본문에 끼워 넣는다.

````markdown
## Diff
!`git diff HEAD`

## 환경
```!
node --version
git status --short
```
````

명령이 0이 아닌 코드로 끝나면 실패하므로, 허용하려면 `|| true`를 붙인다.

### 스킬 내용의 수명

- 발동되면 렌더링된 SKILL.md 내용이 대화에 들어가 **계속 남는다**
- 이후 턴에서 파일을 다시 읽지 않으므로, 오래 유지될 지침처럼 써야 한다
- `allowed-tools` 권한은 다음 메시지를 보내면 사라진다

### 유용한 명령

- `/skills` — 사용 가능한 스킬 전체 목록(위치별)
- `/plugin` — 플러그인 스킬 설치·해제
- 삭제는 해당 폴더를 지우면 끝
- 설정으로 제어: `skillOverrides` (`"on"` / `"name-only"` / `"user-invocable-only"` / `"off"`), `disableBundledSkills: true`

## 6. 좋은 스킬 작성법 (Best Practices)

### 원칙 1 — 간결하게

컨텍스트 윈도우는 **공공재**다. "클로드가 이미 아는 내용인가?"를 매 문단 자문할 것.

```markdown
✅ 좋은 예 (약 50토큰)
## PDF 텍스트 추출
pdfplumber를 쓴다:
(코드)

❌ 나쁜 예 (약 150토큰)
## PDF 텍스트 추출
PDF(Portable Document Format)는 텍스트와 이미지를 담는 흔한 파일 형식입니다.
텍스트를 추출하려면 라이브러리가 필요한데, 여러 라이브러리가 있지만...
```

### 원칙 2 — 자유도를 작업에 맞춰라

| 자유도 | 쓰는 때 | 형태 |
|---|---|---|
| 높음 | 여러 접근이 유효, 맥락에 따라 판단 | 서술형 지시문 |
| 중간 | 선호 패턴은 있으나 변형 허용 | 파라미터 있는 의사코드/스크립트 |
| 낮음 | 깨지기 쉽고 일관성이 결정적 | "정확히 이 명령을 실행하라" |

비유: **절벽 사이 좁은 다리**면 정확한 가드레일(낮은 자유도), **탁 트인 들판**이면 방향만 주고 맡긴다(높은 자유도).

### 원칙 3 — description이 전부다

3인칭으로, 구체적인 트리거 단어를 포함해서 쓴다.

```yaml
# ✅ 좋음
description: Excel 스프레드시트를 분석하고 피벗 테이블과 차트를 만든다. 엑셀 파일, 스프레드시트, 표 형식 데이터, .xlsx 파일을 다룰 때 사용한다.

# ❌ 나쁨
description: 문서 작업을 도와줍니다
description: I can help you process Excel files   # 1인칭 금지
```

### 구조 관련 규칙

- SKILL.md 본문은 **500줄 이하** 유지, 넘으면 파일 분리
- 참고 파일 링크는 **SKILL.md에서 한 단계만** (중첩 참조 금지 — 클로드가 `head -100`으로 일부만 읽을 수 있음)
- 100줄 넘는 참고 파일엔 맨 위에 **목차** 추가
- 경로는 항상 **슬래시(`/`)** — 윈도우식 역슬래시 금지
- 도메인별 폴더 분리(`reference/finance.md`, `reference/sales.md`)로 불필요한 로드 방지
- 파일 이름은 내용을 드러내게: `form_validation_rules.md` (O), `doc2.md` (X)

### 네이밍

- 권장: 동명사형 — `processing-pdfs`, `analyzing-spreadsheets`, `writing-documentation`
- 허용: 명사구 `pdf-processing`, 동작형 `process-pdfs`
- 피할 것: `helper`, `utils`, `tools`, `data`, `files` 같은 모호한 이름

### 워크플로와 피드백 루프

복잡한 작업은 **체크리스트 + 단계별 지시**로 쪼갠다.

```
Task Progress:
- [ ] Step 1: 양식 분석 (analyze_form.py 실행)
- [ ] Step 2: 필드 매핑 작성 (fields.json 편집)
- [ ] Step 3: 매핑 검증 (validate_fields.py 실행)
- [ ] Step 4: 양식 채우기
- [ ] Step 5: 결과 검증
```

**검증 → 오류 수정 → 재검증** 루프를 넣으면 결과 품질이 크게 올라간다.
위험한 배치 작업은 `분석 → 계획 파일 작성 → 스크립트로 검증 → 실행 → 확인` 패턴을 쓴다.

### 스크립트를 쓸 때

- **미루지 말고 해결하라**: 스크립트 안에서 예외를 직접 처리 (파일 없으면 생성 등)
- **근거 없는 상수 금지**: `TIMEOUT = 47  # 왜 47?` ❌ → 값의 근거를 주석으로
- 실행할 스크립트인지 읽을 참고 자료인지 **명시**: "`analyze_form.py`를 실행하라" vs "`analyze_form.py`의 알고리즘을 참고하라"
- 미리 만들어둔 스크립트는 생성 코드보다 **신뢰도·토큰·속도·일관성** 모두 유리
- MCP 도구는 **풀네임**으로: `BigQuery:bigquery_schema`, `GitHub:create_issue`

### 피해야 할 것

- 시점 의존 정보 ("2025년 8월 이전이면 구 API 사용") → `Old patterns` 섹션으로 분리
- 용어 혼용 (field / box / element 섞어 쓰기)
- 선택지 나열 ("pypdf, pdfplumber, PyMuPDF 중 아무거나") → **기본값 하나 + 예외 상황 안내**
- 패키지가 설치되어 있다고 가정하기

## 7. 개발 방법론 — 평가부터 만들어라

문서를 잔뜩 쓰기 **전에** 평가(eval)를 먼저 만든다.

1. **격차 확인** — 스킬 없이 클로드에게 시켜보고, 실패·누락 지점을 기록
2. **평가 작성** — 그 격차를 검증하는 시나리오 3개
3. **기준선 측정** — 스킬 없을 때의 성능
4. **최소한으로 작성** — 격차를 메울 만큼만
5. **반복** — 평가 실행 → 기준선과 비교 → 개선

평가 데이터 예시:

```json
{
  "skills": ["pdf-processing"],
  "query": "이 PDF의 모든 텍스트를 추출해 output.txt로 저장해줘",
  "files": ["test-files/document.pdf"],
  "expected_behavior": [
    "적절한 PDF 라이브러리로 파일을 읽는다",
    "누락 없이 전체 페이지의 텍스트를 추출한다",
    "output.txt에 읽기 좋은 형태로 저장한다"
  ]
}
```

> 공식 실행 도구는 아직 없으므로 각자 평가 체계를 만들어야 한다.

### 클로드 A / 클로드 B 패턴

- **클로드 A**: 나와 함께 스킬을 설계·수정하는 인스턴스
- **클로드 B**: 그 스킬을 실제로 사용하는 새 인스턴스
- 흐름: 스킬 없이 작업해보기 → 반복 제공한 맥락 찾기 → A에게 "이걸 스킬로 만들어줘" → 군더더기 제거 → B로 실전 테스트 → **관찰 결과를 A에게 가져가 개선**

> 클로드는 스킬 포맷을 이미 알고 있어서, 별도 시스템 프롬프트 없이 "스킬 만들어줘"만으로 제대로 된 SKILL.md를 만든다.

관찰 포인트: 예상 밖 탐색 경로 / 참조 링크를 놓침 / 특정 파일만 반복해서 읽음(→ 본문으로 옮길 것) / 아예 안 읽는 파일(→ 불필요하거나 안내 부족)

### 모델별 테스트

Haiku(지침이 충분한가) · Sonnet(명확하고 효율적인가) · Opus(과잉 설명은 아닌가) — 쓸 모델 전부에서 테스트.
새 세션에서 테스트할 것. 작성 중인 세션은 맥락이 남아 결과가 왜곡된다.

---

## 8. 보안 주의사항

> **신뢰할 수 있는 출처의 스킬만 사용할 것.** 직접 만들었거나 Anthropic이 제공한 것.

스킬은 클로드에게 **지시문과 실행 코드**를 주는 것이므로, 악성 스킬은 명시된 용도와 다르게 도구를 호출하거나 코드를 실행시킬 수 있다.

- **전수 감사**: SKILL.md뿐 아니라 스크립트·이미지·리소스 전부 확인. 목적과 무관한 네트워크 호출·파일 접근이 있는지
- **외부 소스 위험**: 외부 URL에서 데이터를 가져오는 스킬은 그 내용에 악성 지시가 섞일 수 있고, 의존 대상이 나중에 변조될 수도 있음
- **도구 오남용 / 데이터 유출** 가능
- **소프트웨어 설치와 동일하게 취급** — 민감 데이터·운영 시스템 접근 권한이 있는 환경에선 특히 신중하게
- 엔터프라이즈는 claude.ai·Cowork 업로드 스킬에 대해 **콘텐츠 스캐닝** 사용 가능 (Skills API·Console 업로드분은 미적용)
- **데이터 보존**: 스킬은 ZDR(무보존) 대상이 **아님**. 표준 보존 정책이 적용됨

## 9. 배포 전 체크리스트

**핵심 품질**

- [ ] description이 구체적이고 핵심 키워드를 포함하는가
- [ ] description에 "무엇을" + "언제"가 모두 있는가
- [ ] SKILL.md 본문이 500줄 이하인가
- [ ] 상세 내용은 별도 파일로 분리했는가
- [ ] 시점 의존 정보가 없는가
- [ ] 용어를 일관되게 썼는가
- [ ] 예시가 추상적이지 않고 구체적인가
- [ ] 파일 참조가 한 단계 깊이인가
- [ ] 워크플로 단계가 명확한가

**코드·스크립트**

- [ ] 스크립트가 문제를 직접 해결하는가 (클로드에게 떠넘기지 않는가)
- [ ] 에러 처리가 명시적이고 도움이 되는가
- [ ] 근거 없는 상수가 없는가
- [ ] 필요한 패키지를 명시했고 사용 가능한지 확인했는가
- [ ] 경로가 전부 슬래시인가
- [ ] 중요한 작업에 검증 단계가 있는가

**테스트**

- [ ] 평가 시나리오를 3개 이상 만들었는가
- [ ] Haiku·Sonnet·Opus에서 테스트했는가
- [ ] 실제 사용 시나리오로 테스트했는가
- [ ] 새 세션에서 테스트했는가

## 10. 빠른 시작 예제

`~/.claude/skills/summarize-changes/SKILL.md`:

````markdown
---
description: 커밋하지 않은 변경사항을 요약하고 위험해 보이는 부분을 짚어준다. 사용자가 무엇이 바뀌었는지 묻거나, 커밋 메시지를 원하거나, diff 리뷰를 요청할 때 사용한다.
---

## 현재 변경사항

!`git diff HEAD`

## 지시사항

위 변경사항을 2~3개 불릿으로 요약한 뒤, 누락된 에러 처리·하드코딩된 값·업데이트가 필요한 테스트 등
눈에 띄는 위험 요소를 나열하라. diff가 비어 있으면 커밋할 변경사항이 없다고 답하라.
````

테스트: 아무 git 프로젝트에서 파일을 조금 고치고 `claude` 실행 → "뭐가 바뀌었어?" 또는 `/summarize-changes`
